### 1. GRAPHICA vs. PACIFISTA
* **O-RAN Tier & Placement:** PACIFISTA operates offline at the **Service Management and Orchestration (SMO) / Non-RT RIC** layer (>1 s timescale). GRAPHICA operates online directly inside the **Near-RT RIC** (10 ms–1 s timescale).
* **Operational Mechanism:** PACIFISTA is a **pre-deployment admission control gatekeeper**; it profiles Empirical Cumulative Density Functions (ECDFs) in a sandbox and blocks xApps if their predicted KPI severity index ($\sigma_K$) exceeds a tolerance threshold ($\delta_{\text{TOL}}$). GRAPHICA is a **real-time event-driven classifier**; it encodes live state transitions into binary vectors ($S_t$) and uses a Graph Convolutional Network (GCN) with Focal Loss to predict conflicts and run Root Cause Analysis (RCA).
* **Data & Profile Requirements:** PACIFISTA requires developer manifests and environmental profiles collected across predefined operational conditions ($\mathcal{C}$). GRAPHICA is distribution-independent and engineered to handle imbalanced live telemetry data directly.
* **Testing Environments:** PACIFISTA was evaluated on a **hardware-in-the-loop wireless emulator (Colosseum + OpenRAN Gym)**, whereas GRAPHICA was tested on **synthesized/simulated datasets**.

### 2. GRAPHICA vs. A2C Scheduler
* **Shared Operating Tier:** Both frameworks process E2 interface telemetry/parameters and operate live within the **Near-RT RIC**.
* **Functional Roles:** GRAPHICA is a **predictive anomaly detector and diagnostic tool** (GCN + RCA) that can be paired with a simple priority-based policy for evaluation. The A2C Scheduler is an **active closed-loop policy coordinator and mitigation engine**.
* **Working Principle:** GRAPHICA predicts impending conflicts at timestamp $t_1$ before physical KPI degradation occurs at $t_3$. The A2C Scheduler uses Advantage Actor-Critic Reinforcement Learning to dynamically select active xApp masks ($\mu^\dagger$) or toggle baseline fallback policies based on physical context variables (traffic load, user mobility speed).
* **Testing Environments:** Both frameworks have been evaluated primarily in **custom software/simulation environments**.

### 3. A2C Scheduler vs. QACM (Recommended Direct Comparison)
* **Shared Functional Objective:** Both are active, closed-loop runtime mitigation engines residing inside the **Near-RT RIC** that issue direct control directives over the E2 interface to protect network Quality of Service (QoS).
* **Mitigation Granularity (Macro vs. Micro):** 
  * **A2C Scheduler (Macro-Level Action Coordination):** Dynamically toggles which pre-trained xApps (or baseline equal-allocation policies) are active ($\mu^\dagger$) based on context, without modifying the internal parameters generated by the xApps.
  * **QACM (Micro-Level Parameter Bargaining):** Intercepts conflicting numerical requests for shared input parameters (e.g., transmit power, RET) and uses game-theoretic optimization/heuristics to calculate an optimal compromise value ($p_l^{\text{opt}}$).
* **QoS Enforcement:** The A2C Scheduler optimizes overall system transmission rate and reduces discarded bits. QACM converts KPIs into standardized z-score utilities to explicitly guarantee that individual xApp QoS thresholds ($q'$) are satisfied.
* **Processing & Training Overhead:** The A2C Scheduler relies on fast forward-pass DRL inference. QACM requires running forward-pass predictions across Artificial Neural Network (ANN) regression models and solving a constrained optimization problem or heuristic search ($O(N \cdot |X'|)$ complexity).
